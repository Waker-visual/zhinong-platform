# 每日经营简报与主动预警指南

本功能仅使用项目已有的虚构演示数据，面向“打开首页就知道今天先做什么”的使用方式。模型解读、规则检测与数据库统计分别标明来源；没有真实设备验证或经营效果承诺。

## 使用入口

1. 用租户账号登录，选择一个农场，在“今日农场”或“经营总览”查看“今日经营简报”。
2. 点击“查看完整日报”，查看综合解读、优先事项、数据依据和缺失信息，可选择最近十四份报告的日期。报告日期和生成时间标明快照时点；实时设备状态以顶部预警中心为准。
3. 点击建议旁的入口进入农事、种植计划或预警；“询问 AI”会把建议、依据和日期带入对话草稿，核对后发送。
4. 打开顶部“提醒”，查看异常原因、检测窗口及排查步骤。管理员和操作员可以确认知晓、填写说明并转为田间问题，沿用现有派工、执行回执与人工复核流程；查看者可阅读和询问 AI。

首页不会自动弹出遮挡操作的报告。提醒入口显示当前农场未关闭的告警，新告警在页面内提示，避免每次轮询重复打扰。网页在后台时暂停提醒轮询，返回后更新。当前通知范围是打开的网页，没有短信、微信或关闭网页后的系统推送。

## 每日报告如何生成

- 默认按 `Asia/Shanghai`（UTC+8）计算报告日期。服务运行时从每日 06:00 起检查当天尚未生成的农场；首次访问当天报告也会补齐。停止服务期间不会运行，恢复后补齐当天，不伪造过去日期的历史快照。
- 每个租户、农场、日期最多一份报告，数据库唯一约束防止并发重复。刷新页面读取已保存报告，不反复消耗模型调用。
- 先保存确定的事实和规则行动清单，首页立即可读；单独、有界的后台工作队列调用已有模型网关补充解读。模型请求不会占用灌溉停止检查的调度线程。
- 报告包含：有效在种计划、待办/逾期农事、近七天已登记收获量与记录数、未关闭现场问题、在用设备、新鲜农情测点、离线/过期设备和告警，以及优先事项、四情提示、证据与资料缺口。
- 状态为等待分析、分析中或已完成；来源明确区分 `LLM` 模型解读和 `RULE_ENGINE` 规则分析。未配置、超时、认证失败等只展示脱敏诊断，不输出凭据或上游错误正文。中断超过十分钟后保留事实报告并结束等待，不重复可能已完成的模型请求。
- 报告保存在业务数据库的 `ai_farm_briefings` 表。历史查询返回最近十四份报告，旧记录不会由本功能自动删除。H2 与 MySQL 初始化脚本均包含新增表，无需删除既有数据库。

日报描述的是生成时的经营情况；当天后续发生的告警不会修改已保存的事实快照。通过预警中心或 AI 实时工具核查变化。

## 三类预警与恢复

| 类型 | 判定依据 | 处理方向 |
| --- | --- | --- |
| 监测值异常 | 最新有效上报超出设备通道已配置的上下限 | 复测、检查安装与校准，结合地块和作物阶段核实生产原因 |
| 设备离线 | 距最后接收时间超过 `max(180秒, 上报周期×3)`；新设备有接入宽限期 | 检查电源、网络、网关和接入服务；模拟设备先采集并检查模拟数据流 |
| 采样数据过期 | 仍收到上报，但已配置通道缺测、采样过期或来源与接入方式不符 | 检查通道、采样任务与设备时钟，补充当前完整读数 |

维护、停用、手工录入设备和已归档农场不按自动在线设备检测。无创建记录的历史设备在首次监测时登记宽限起点，避免刚启用检查就误报。设备离线时不同时重复提示采样过期；恢复接收后关闭离线事件，仍旧过期的采样继续单独跟踪。同一持续故障复用同一事件编号，保留确认状态。

农情分析还采用最长十五分钟的决策数据窗口；采样时间、接收时间及数据来源都须有效。切换设备接入方式后，原方式的旧读数不会再作为新鲜农情依据。两个自动检查模块均使用独立工作线程，避免阻塞已有灌溉限时停止检查。

设备正被采集或控制事务更新时，告警扫描保留既有记录并跳过本次检查，待后续采集完成或下一轮检测后更新，避免打开工作台或提醒时因争用设备锁而读取失败。

确认知晓只表示有人接手，不能使读数恢复正常。重新上报正常值自动关闭对应阈值告警，设备接收及所有已配置通道恢复后自动关闭对应健康告警。未关联地块的设备需先在设备台账关联地块，才能转田间问题。恢复告警也不会代替已经创建的田间问题的人工复核。

## AI 对话的增强

流式对话可以调用七个白名单只读工具：经营概况、待办农事、现场问题、天气四情、设备异常与离线、收获对比和今日简报。模型给出的租户/农场参数不参与查询，农场范围取自当前已鉴权的对话记录。

收获工具对比最近两个完整的三十天窗口，不包含当天，并返回记录数、已登记公斤数及近期分地块明细。收获登记量不等于单产或利润；无记录不等于零产出，不同作物与批次不能直接作经营因果比较。日报工具只读已有报告，不会递归发起模型生成。

适合演示的问题：

- “结合今天的简报、设备告警和待办农事，排出今天最先做的三件事，说明依据与复核方法。”
- “这台设备掉线后，哪些生产判断需要暂停？应该按什么顺序排查？”
- “对比近两期收获记录，哪些变化可以确认，哪些还需要补充成本或作物资料？”

工具查询会显示在现有活动时间线中。对话没有新增设备写入权限；灌溉仍走已有人工审批入口，不能仅凭对话自动操作设备。

## 运行配置

保持默认配置即可启用。以下为 Spring 属性，可通过启动参数 `--属性名=值` 覆盖；生产凭据仍只写入既有私有配置。

| 属性 | 默认值 | 用途 |
| --- | --- | --- |
| `farm.ai.briefing-enabled` | `true`（未单独设置时随 `farm.ai.automation-enabled`） | 自动检查当日日报；关闭后仍可首次访问生成 |
| `farm.ai.briefing-check-ms` | `60000` | 每日 06:00 后的检查间隔 |
| `farm.alerts.automation-enabled` | `true` | 后台设备健康扫描；读取预警仍会检查当前范围 |
| `farm.alerts.scan-delay-ms` | `60000` | 设备健康扫描间隔 |
| `farm.alerts.initial-delay-ms` | `60000` | 启动后首次健康扫描延迟 |

## 演示与验收

使用已有演示启动脚本重新构建并启动，凭据沿用本机私有配置。选择演示农场后：

1. 展开今日经营简报，检查数字与农事、收获台账一致；连续刷新后报告编号与日期不变。
2. 查看规则/模型来源、时间与数据缺口，再从一条优先事项进入对应业务页面。
3. 在设备台账选择模拟设备并采集，查看正常状态；停止该设备的持续上报后等待判定窗口，打开预警查看离线证据和修复步骤。
4. 确认知晓，再转为田间问题；检查问题与告警只关联一次。恢复采集后验证告警恢复，并继续完成田间问题的人工复核。
5. 从告警发起 AI 草稿，发送后查看工具活动与带依据的回答。切换农场确认简报、提醒和草稿都属于新农场。
6. 使用另一租户、查看者和平台账号验收：跨租户请求拒绝、查看者不能确认/派工、平台账号不能读取经营报告与告警。

仓库验证入口为 `scripts/verify.ps1`，包含后端集成测试、前端构建、项目检查工具、手机/Android 检查、敏感信息与 MySQL 结构一致性检查。新增测试覆盖日报幂等及权限、模型成功/回退、告警去重/恢复/范围、对话工具作用域和收获统计边界。

2026-10-12 本次验收：完整脚本通过，160 项后端测试成功、12 项独立 MySQL 测试按环境条件跳过；最终 AI/日报定向回归 49 项通过，前端构建及公开范围扫描通过。隔离内存数据库的浏览器验收覆盖桌面与 390px 页面、日报详情、预警确认/转问题/跳设备、只预填不自动发送的 AI 草稿、平台屏蔽、查看者只读和键盘关闭弹窗。浏览器未发现错误，页面及两个弹窗没有横向溢出。浏览器实例关闭模型服务，验证了规则回退；模型成功及跨日历史由受控后端集成测试验证，未把它们表述为在线模型或真实硬件的现场验收。

## 采用的技能与工作流程

本次检索并核查了 [Anthropic 官方 webapp-testing 技能](https://github.com/anthropics/skills/tree/main/skills/webapp-testing)，采用其“观察已渲染页面、再操作、最后检查结果”的浏览器验收流程；界面设计使用本机 `frontend-design`，浏览器操作使用本机 `agent-browser`。没有将远程技能代码作为项目运行时依赖，也没有复制技能源码进仓库。

参考 [Anthropic《Building effective agents》](https://www.anthropic.com/engineering/building-effective-agents) 的可组合工作流程、工具增强和有界执行原则，将证据采集、确定性检查、模型解读与人工执行分开。这里的设备异常检测是规则引擎，综合解读才由模型生成，不把固定规则包装为模型推理。
