# 云数据库接入与两年学术演示

本版本支持本地 H2，以及 MySQL 8.0.16+ / 8.4（含兼容版本的云 RDS）。项目只包含通用接入代码、空白配置模板和虚构数据生成规则，没有内置云端地址、账号或口令。没有填写配置时，默认本地启动方式仍使用 H2；添加接入模块不代表某个云端实例已经连接成功。

## 填写自己的数据库信息

1. 在 MySQL 或云控制台准备一个专用于本项目的空数据库，字符集使用 `utf8mb4`。为该库创建专用账号，初始化需要 `SELECT、INSERT、UPDATE、DELETE、CREATE、INDEX、REFERENCES` 权限；不要使用其他项目的数据库。配置云端网络规则允许应用服务器访问数据库端口。
2. 复制项目中的空白模板，填写副本：

   ```powershell
   Copy-Item config/database.example.properties config/database.properties
   ```

   副本中的 `farm.database.host`、`port`、`name`、`username`、`password` 分别填写主机名、端口、数据库名、用户名、口令。不要填写公开的 `database.example.properties`。副本和本机原有的 `rds.txt` 已被 Git 忽略；检查工具也会阻止这些文件或已填写的模板提交。

3. 云连接默认使用 `VERIFY_IDENTITY`，同时校验证书和主机名。若供应商使用私有 CA，请将其可信证书安装到应用 JVM 的信任库，或通过 JVM 配置指定本机信任库；不要把证书私钥、信任库口令提交到项目。不要通过关闭校验来解决云端证书错误。[MySQL 官方证书认证说明](https://dev.mysql.com/doc/connector-j/en/connector-j-server-authentication.html)
4. 停止当前占用 9175 端口的后端，在项目根目录启动：

   ```powershell
   .\scripts\start-cloud.ps1
   ```

   以后代码未变化可加 `-SkipBuild`。也可通过 `-ConfigPath` 指定项目外的私有 `.properties` 文件。脚本没有云端信息，不会读取 `rds.txt`；连接失败会报错，**不会悄悄退回 H2**。服务终止后恢复脚本调用前的环境配置。

空数据库首次启动会创建表、账号和完整研究演示场。初始化口令沿用本机 `.cache/demo-password.txt`，没有时生成随机口令保存到该文件；也可自行设置 `FARM_BOOTSTRAP_PASSWORD`。已有数据库的账号密码不会被重置。登录租户 `demo-a`，账号 `admin` / `operator` / `viewer`。

当前 MySQL 建表脚本支持本版本的空库初始化与重复启动，不负责改造其他应用或未知旧结构。将来改变表结构时应提供对应迁移，不能用删除数据库的方式升级。

## 确认数据到底存在哪里

登录后打开 **账号设置 → 个人资料 → 数据存储**，页面显示实际连接的引擎和本机/远程位置。该信息来自当前业务数据库连接，不是配置文件的猜测。

认证接口 `GET /api/system/database` 返回 `engine`、`location`、`connected`，不返回地址、账号、口令和其他租户数据。再创建或处理一项演示任务、刷新页面检查保存结果，可验证实际业务写入。

首次初始化完成前，业务接口返回 503 和初始化提示，不会返回一个尚未补完的空农场。无需登录的 `GET /api/health` 只返回就绪状态；返回 200 且 `ready=true` 后再登录。

MySQL 模式下，核心业务、研究演示和经营模拟使用同一个配置的 MySQL 数据库。本地 H2 模式仍可沿用原有独立本机 MySQL 模拟库；只连接模拟库不等于将核心业务迁到云端。

已有本机 H2 中的手工记录**不会因填写云连接而自动迁移**。新空云库会生成同一套研究场景；本机数据库和账号仍保留。若需要保留所有既有手工业务，应先备份并单独进行数据迁移验收，不能把两份库的统计当成已经同步。

## 两年数据是如何构造的

默认启动脚本同时开启 `FARM_RESEARCH_HISTORY=true`，在 `demo-a` 的 **青禾设备联动演示场** 中初始化，其他农场和租户保持原样。

- **时间范围**：首次生成日向前两年；以后重启保留这段历史及用户操作，不把日期整体平移。新数据库换一个生成日期时，当前任务和历史范围也会相应变化。
- **种植季**：两个水稻地块按每年 5 月 15 日至 9 月 25 日构造单季；冬季为休耕巡检。第三个地块假设为具备环境控制的设施叶菜区，按约 7–9 周生长、7 天间隔轮作。地理位置仍只是虚构布局，不代表该地区的实测作物制度。
- **农事记录**：种植季内包含播种、供水、养分管理、巡查与植保任务，另有连续每周巡检；完成任务包含执行人、时间、面积和回执。当前保留逾期、受阻、资源待落实与待复核场景，供真实操作软件流程。
- **收获关联**：每条研究产量记录通过 `production_lineage` 关联同租户、同地块的种植季和已完成收获任务，收获日期在种植周期内。水稻每季一次，叶菜分三批。
- **产量假设**：水稻每亩约 510–604 kg、叶菜每轮每亩约 1600–2099 kg，按面积和确定性公式计算。这些数值只是构造参数，没有经过田间标定，不可当作真实产量或模型预测准确性证据。
- **设备覆盖**：沿用原有设备，给缺少土壤水分监测的地块补上模拟监测点，三个地块都有对应墒情数据。
- **监测历史**：较早历史每天一个快照，近 30 天每半小时一个样本；温度包含季节和昼夜变化，湿度、土壤水分与假设降雨共同变化，夜间光照为零。降雨量为当天累计值，日界重置。历史控制设备以待机快照为主，不冒充实体设备操作记录。
- **累计值和控制**：研究初始化纠正旧模拟用水/用电计数的回退；持续采集保留累计计数和最后控制反馈，不靠周期波动修改闸门开度或泵状态，也不自行发送控制指令。累计用量不是费用核算或水电计量模型。

生成日期和数据版本保存在 `demo_research_farms` 中；同一生成日期与地块名称对应同一套数值规则，数据库行 ID 仍使用随机 UUID。算法位于 `ResearchDemoData` 与 `ResearchSignals`，属于可复现的软件展示数据，不是采集到的研究样本。

## 如何检查空白和失真

“今日农场”增加 **两年学术演示** 说明，可查看历史范围、记录数量和检查结果；“农场概览”新增 **近两年** 统计范围。种植计划、农事任务和生产记录均可查看相应历史。

`GET /api/farms/{farmId}/research-data` 仅对当前租户农场返回统计和检查项：

- 种植季是否重叠；
- 收获是否缺少关联、跨地块、超出种植日期或与任务面积不一致；
- 是否存在未来日期的收获；
- 模拟累计计数是否下降；
- 地块是否缺少土壤水分监测。

结果为零表示这些检查没有发现问题，不表示所有农业假设已经得到实证验证。用户新建的未关联产量记录会提示复核；休耕季没有收获、没有未处理告警等零值本身也可能合理。

只有旧版自动演示且没有业务修改迹象的场景才会升级替换；有用户修改的旧记录会保留，接口返回未启用研究场景的说明。升级已有实例前，应停止后端并备份 `backend/data/zhinong.mv.db` 和旧应用包，备份留在 Git 忽略的 `.cache/backups/`。修改已生成历史不会被重启覆盖。

服务运行时每分钟采集模拟设备，每天首次检查补充当天巡检待办。不会补造停机期间已完成作业，也不会自动新增收获或关闭问题。关闭持续采集可设置 `FARM_DEMO_LIVE=false`；关闭首次研究场景生成可在本地启动前设置 `FARM_RESEARCH_HISTORY=false`，既有历史不删除。

## 验证方式

```powershell
# 后端、前端、检查工具、坐标与敏感信息检查
.\scripts\verify.ps1
# 真实 MySQL 兼容回归，使用独立的本机临时库，不接入云端
.\scripts\verify-mysql.ps1
```

MySQL 回归需要先按原有 `setup-simulation-db.ps1` 说明准备本机 MySQL 环境。验证脚本为每次运行创建随机命名的专用测试库和账号，测试结束只删除本次创建的库与账号。覆盖两年场景、登录和租户隔离、业务回执、模拟控制、时间精度、历史曲线与数据检查。云端的网络白名单、证书和实际账号权限仍须填写信息后实地验证。

2026-10-08 本机验收：74 项 H2 后端测试、6 项真实 MySQL 集成测试、前端构建、6 项项目检查工具测试及 2 项坐标测试通过。另使用隔离的本机 MySQL 8.4.9 实测了 `start-cloud.ps1` 的私有配置启动入口，核心业务与模拟模块均使用该 MySQL。未使用或验证真实云端凭据。本机实际演示场包含 468 项任务、37 条收获、18 条种植计划、43 项巡田问题和 11 台模拟设备，五项数据检查均未发现问题；重复启动后数据保留，持续采集已验证。

时间兼容参照 [MySQL Connector/J 时间处理说明](https://dev.mysql.com/doc/connector-j/en/connector-j-connp-props-datetime-types-processing.html)，`start-cloud.ps1` 连接会话使用应用当前时区的数值偏移，避免依赖 MySQL 命名时区表。兼容的 `start-rds.ps1` 入口保留其显式 UTC 配置。建议应用服务器使用固定业务时区（本项目本机验收为 UTC+8），既有数据库不要直接换入口或时区，先另做日期和时间迁移验证。

合并后的通用 30 天采集器会跳过 `demo_operating_farms` 已登记的农场，这些农场继续由经营/研究场景采集器维护。其他虚构演示农场仍持续补齐数据；不会用模拟值填补真实设备的缺测。
