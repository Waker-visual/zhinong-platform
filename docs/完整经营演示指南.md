# 完整经营演示指南

> 2026-10-08：本指南中的数量对应旧版经营演示。默认启动现使用两年研究场景，并已加入完整 MySQL 接入模块。当前数据规则、云配置和验证步骤请参阅 [云数据库接入与学术数据说明](云数据库接入与学术数据说明.md)。本机 H2 仍是本地启动的默认存储。

## 进入有历史的农场

在项目根目录运行：

```powershell
.\scripts\start-demo.ps1
```

浏览器访问 `http://127.0.0.1:9175/`，以租户 `demo-a` 的 `admin`、`operator` 或 `viewer` 登录。密码沿用本机初始化账号；未修改过的初始口令保存在 Git 忽略的 `.cache/demo-password.txt`，不要复制到公开文档或提交到仓库。

登录后默认选中 **青禾设备联动演示场**。若已选其他农场，可在顶部农场选择器中切换。更新正在运行的旧版本后，刷新浏览器以加载新页面。管理员可以查看与处理全部农场待办；操作员侧重自己的任务；查看者只读。

## 首次补充的数据

数据全部虚构，以首次升级启动当天为基准生成历史与当前工作，保留已有地块、设备、账号及用户记录。

| 内容 | 首次场景 |
|---|---|
| 地块与设备 | 沿用 3 个地块、9 台模拟设备及其地图位置 |
| 种植周期 | 11 条：水稻往季、当季，以及叶菜连续轮作 |
| 收获台账 | 20 条：往季水稻和多批叶菜采收；关联同日收获任务说明 |
| 农事任务 | 66 项：57 项已完成、8 项待处理、1 项已取消 |
| 当前任务 | 6 项待开始、2 项执行中；含 1 项逾期、1 项受阻及待落实资源的安排 |
| 巡田问题 | 7 项：3 项已复核关闭、4 项未关闭；含作业完成后等待管理员复核的问题 |
| 作业记录 | 负责人、计划与执行记录，完成面积、回执、时间；问题复核由管理员记录 |
| 监测历史 | 气象、墒情、水情、虫情设备补充前 14 天逐小时虚构读数 |

历史任务与收获不是模型预测，也不代表真实农场的生产经验。作业方式、产量和记录中的处理方法均用于软件流程展示，不是农艺处方。若原有种植计划与演示周期重叠，优先保留原计划，种植条数可能少于表中值；用户操作和后续每日待办也会使数量变化。

## 建议查看顺序

1. **今日农场**：查看逾期待办、执行中任务、资源缺口、现场问题；可为任务落实作业方式、报告受阻或填写完成回执。
2. **经营总览**：查看任务进度、问题数量、生产趋势与监测状态。
3. **农事任务 / 作业记录**：查看历史任务与负责人、面积、回执和操作时间。
4. **种植 / 生产记录**：查看往季水稻、叶菜轮作和分批收获台账。
5. **地图 / 设备**：查看相同农场中的地块、监测曲线及模拟闸门、泵房反馈。

完成处理任务后，关联现场问题仍须管理员填写复核依据并关闭。记录会持久保存，重启不会把已完成任务重新置为待办。

## 持续演示如何工作

启动脚本默认设置 `FARM_DEMO_LIVE=true`。服务运行期间每分钟检查一次，仅采集 `demo-a` 中已登记经营演示场、原始 `DEMO-CTRL-` 编码且仍处于启用状态的模拟设备。维护、停用、改为 HTTP 或人工接入的设备不会被自动采集。闸门开度、泵运行等控制反馈保留最后状态，采集不会自行下发控制指令。

每天首次检查时，为当天添加两项巡检待办；间隔多天未运行时只补当天，不堆积停机期间的任务。服务不会自动完成任务、关闭巡田问题或新增收获量。刷新页面即可查看最近采集和新增待办；服务停止后读数随时间变旧属于正常现象。

仅启动脚本默认开启持续采集，直接运行应用时 `FARM_DEMO_LIVE` 默认关闭。一次性历史补充要求 `FARM_DEMO=true` 且 `FARM_DEMO_RICH=true`（后者默认开启）；关闭持续演示不会删除既有数据。

```powershell
# 先停止当前服务，再以关闭持续演示的配置启动
$env:FARM_DEMO_LIVE = 'false'
.\scripts\start-demo.ps1 -SkipBuild
```

将该环境变量设回 `'true'` 并重启即可恢复。代码更新后首次启动应重新构建，不要使用 `-SkipBuild`。首次历史补充由数据库登记表标记，重复启动不会重复导入；不要删除登记或数据库来刷新日期，否则可能产生重复数据或丢失用户记录。

## 为什么以前会显示 0

原来的设备联动演示场只初始化设备、地块和一次性读数，没有为该农场建立农事、种植与生产历史。因此连接数据库成功并不会自动产生待办和收获记录。旧读数超过设备新鲜度窗口后，也会让“正常上报”变成 0，设备资产本身仍存在。

核心业务默认使用本机 `backend/data/zhinong.mv.db`；配置独立 MySQL 模拟库只影响经营模拟模块，不会把核心业务迁移到云数据库，也不会导入历史生产记录。`rds.txt` 等说明文件不会被启动脚本自动读取。新版提供 `start-cloud.ps1` 将核心业务和模拟模块一起接入配置的 MySQL 数据库，使用方法见新版云数据库指南。

## 升级、备份和验证

对已有本机实例升级前，停止使用该数据库的后端进程，再把 `backend/data/zhinong.mv.db` 和旧版 `backend/target/zhinong-platform-0.3.0.jar` 复制到 Git 忽略的备份目录，例如 `.cache/backups/`。备份可能含账号、会话与业务记录，不得提交。运行启动脚本重新构建并启动，在上述页面检查数据和任务处理流程。

需要回退时先停服务，再成对恢复升级前数据库与旧应用包，以旧应用包启动；仅恢复旧代码无法撤销已新增的数据。独立 MySQL 模拟库不在本次补充范围。

项目根目录运行 `scripts/verify.ps1`。新增集成测试覆盖经营接口中的历史/当前数据、租户隔离、平台访问限制、重复初始化保留用户修改、每天只生成一次待办、模拟采集范围、维护/HTTP 设备跳过及控制反馈保留。前端构建、项目检查工具、坐标测试和敏感信息扫描仍由同一脚本执行。
