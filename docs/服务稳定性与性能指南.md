# 服务稳定性与性能指南

本项目继续采用 Vue + Spring Boot 的模块化单体结构，支持 H2 演示库和 MySQL。经营查询始终由已认证身份确定租户；平台账号只读取技术运行指标，不能读取农场经营数据。所有农场、设备与生产数据均为虚构演示数据。

## 本轮定位与处理

大屏原先并行发出六个请求，却等到所有请求结束才更新界面。实测单个农场的运行趋势需约 4.8–5.8 秒，智能农情需约 1.9–3 秒；两路并发刷新时整轮约 10.4 秒。查询会遍历历史测点取最新值，并把大量采样搬到 Java 再聚合。慢瓦片还会占用浏览器同源连接及后端请求线程。

第一轮聚合改写后仍存在秒级等待。继续对停机备份的独立副本执行 `EXPLAIN ANALYZE`，发现 H2 将几条关联查询从遥测表起扫，每条访问同租户约 96.6 万行。将已认证租户与当前农场条件明确放在设备表，并保留遥测关联的租户相等条件后，查询先定位设备，再读取索引覆盖的时间窗口。副本上水分趋势与日矩阵从约 1.64 秒降至 12–13 毫秒；这只是定位样本，交付效果以运行服务的 HTTP 对照为准。

- **数据查询**：按设备、指标和时间索引查最新值，趋势和每日矩阵在数据库聚合；历史缺口、有效零值、样本加权平均、日期边界及租户范围保留。工作空间、预警中心、日报和 AI 工具都只读取已保存的告警；设备接收与后台巡检（默认每 60 秒）更新告警，读取请求不再触发巡检写入（见下一节）。
- **部署时区**：智能农情的七日天气与虫情统计统一按北京时间取窗口和分组，服务器使用 UTC 时也不会多出第八个日期；H2 与 MySQL 共用跨午夜、窗口首日及未来样本排除回归。全部业务“今天”另由统一业务时钟按 `farm.zone` 计算，见下文“业务日历与时区”。
- **用户时间**：消息时间与会话历史分组按用户本地日历展示，测试使用本地日期构造样本，保留 ISO 时间的绝对时刻。73 项 AI 前端测试分别在 UTC、上海和纽约时区通过。跨时区完整验证需同时设置测试进程的 Java 时区与 Node `TZ`，两者互不替代。
- **界面读取**：六个模块独立呈现，刷新不重复叠加；切换农场、隐藏或关闭大屏会取消未完成请求并屏蔽迟到结果。同一农场刷新失败时保留旧快照及原读取时间，明确标示失败并支持只重试失败项。鉴权失败清除受保护数据。
- **地图隔离**：浏览器最多同时读取 4 张瓦片、等待队列最多 48 项；后端使用 12 个专用任务槽且不排队，重复瓦片共享请求，异步响应释放 HTTP 工作者。每个固定上游有覆盖完整响应体的 12 秒期限，超时或线程中断会取消底层 HTTP 请求，防止供应商只发响应头后永久占槽。容量耗尽返回 503，失败瓦片退避 5 秒；成功缓存与失败缓存各有 256 项上限。卫星来源和署名保留。
- **资源期限**：数据库连接等待默认 3 秒，业务 JdbcTemplate 每条语句默认 10 秒；暂时性连接、锁和查询超时返回 503 与 `Retry-After`，不暴露连接详情。不会自动重试写操作。正常关闭支持最长 20 秒的请求收尾；强杀进程、断电不能获得这一保证。
- **AI 流式对话**：准备上下文前最多准入 8 个活动运行，模型网关仍独立限制为 3 个并发。准备事务的累计 SQL 预算为 10 秒，整轮预算为 65 秒，包含准备时间；准备阶段在 SQL 执行点检查事务剩余时间，异步阶段通过定时器发出取消，均不承诺强制中止任意 Java 代码。取消和超时后，已运行的工作线程真正退出才释放名额；尚未开始或提交失败的任务立即归还。客户端只有流式接口确实不存在（404/405）时才走兼容路径，服务繁忙时不会再发同步生成请求。
- **后台调度**：普通业务任务、灌溉停止检查与 AI 截止计时器分别调度，慢演示采集不能占据停止检查的计时线程。软件保护仍依赖数据库与设备通信可用，真实设备必须具备独立硬件保护。

## 2026-10-15：告警读取、研究报告与设备锁

**现象**：全新 `start-demo` 实例初始化后，刚登录时顶栏显示“离线”、页面提示“无法连接本地服务”，但服务本身正常；研究数据报告间歇返回 503；H2 跟踪日志出现 `devices ... FOR UPDATE` 锁超时。

**根因**（在演示库停机副本上用 `EXPLAIN ANALYZE` 逐条确认）：

- `GET /api/alerts` 每次读取都先执行写入式设备健康巡检，不带 `farmId` 时逐台检查整个租户（约 80 台设备），耗时超过前端默认 15 秒期限；前端把超时当作离线。
- H2 2.2 在遥测表上优先选择外键自带的 `(tenant_id, device_id)` 索引，即使 `ix_telemetry_latest`、`ix_telemetry_history` 的全部等值列都已给定。每次“取某通道最新值”因此读取并排序该设备全部历史（演示泵站约 2.8 万行、5,964 页），而写入遥测、告警检查、演示采样都会在持有设备行锁时按通道调用它。
- 研究报告的“累计量回退”检查从遥测表按租户起扫：为找出单个农场约 4,300 条电量/累计水量样本，扫描了租户全部约 76.4 万行（16 万页）。运行一段时间、页面缓存被挤出后超过 10 秒语句期限，返回 503。
- 设备行锁被持有数秒，其他同样 `FOR UPDATE` 的采样或检查等待超过 H2 锁期限，即日志中的锁超时。

**处理**：

| 位置 | 改动 | 单次访问（副本 `EXPLAIN ANALYZE`） |
|---|---|---|
| 告警读取 | `GET /api/alerts` 改为只读已提交的告警，含日报、AI 工具；巡检只由设备接收路径和 `DeviceAlertTicker` 执行 | 不再写入 |
| 通道最新值 | H2 指定 `ix_telemetry_latest`，`ORDER BY` 按索引列顺序书写，按索引顺序读第一行即停 | 28,198 行 → 1 行（5,964 → 6 页） |
| 演示经营采样 | 设备最近采样时间改为 `ix_telemetry_device_time` 首行读取，不再对全部历史求 `MAX` | 28,198 行 → 1 行 |
| 累计量回退检查 | 从当前农场设备出发，按指标逐个经 `ix_telemetry_history` 读取 | 764,253 行 → 2,185 行（每个指标） |

索引提示只用于 H2；MySQL 已按复合索引执行，不加提示。`ix_telemetry_history (tenant_id, device_id, metric, measured_at)` 早已存在，无需新增索引或迁移。所有查询仍以已认证租户为条件，设备、遥测关联保留租户相等条件。

**前端**：请求超时不再标记为离线。连接失败或网关 502/503/504 仍显示红色“连接中断”；超时显示橙色“响应超时 · 点击重试”，页面提示“本地服务响应超时，可能仍在处理”；下一次收到任何响应即恢复“已同步”。

**取舍**：预警中心不再在打开或轮询时触发巡检。离线判定窗口至少 180 秒，后台巡检默认每 60 秒一次（启动后首轮延迟 60 秒，见 `farm.alerts.*`），新离线告警最多晚一个巡检周期出现；设备上报、阈值告警与恢复仍在接收时立即更新。累计量回退检查覆盖完整历史，持续采样会让每个计数通道每天增加约 1,440 行；读取量随该农场计数通道样本线性增长，但不再随整个租户增长。

**实测**：同一台 Windows 开发机，`$env:FARM_PORT='9186'` 后运行 `scripts/start-demo.ps1 -SkipBuild`，每次使用全新数据库，初始化完成后依次请求 3 轮：`GET /api/alerts`（不带农场）、5 个农场各自的 `GET /api/alerts?farmId=` 与 `GET /api/farms/{id}/research-data`。随后 3 路客户端连续 3 分钟请求 `GET /api/alerts`，再复测 2 轮。

| 接口 | 修改前（fcabc81） | 修改后 |
|---|---:|---:|
| `GET /api/alerts`，P50 / 最大 | 5,488 / 6,525 ms | 14 / 19 ms |
| `GET /api/alerts?farmId=`，P50 / 最大 | 1,266 / 2,207 ms | 8 / 16 ms |
| `research-data`，P50 / 最大 | 3,016 / 5,437 ms | 24 / 49 ms |
| 加压 3 分钟：`GET /api/alerts` 次数，P50 / 最大 | 849 次，18 / 18,456 ms | 45,894 次，15 / 31 ms |
| 加压后：`GET /api/alerts`，最大 | 42,992 ms | 15 ms |
| 加压后：`research-data` 成功率 | 1/10（其余 503，约 10 秒） | 10/10（最大 31 ms） |
| H2 跟踪日志 | 9 次语句超时、1 次 `DEVICES` 锁超时 | 无 |
| 修改后持续运行约 4.5 小时复测：三类接口最大 | — | 18 / 17 / 59 ms，10/10 成功，跟踪日志仍无错误 |

修改前后各次请求均由本机脚本发出，只记录状态码与耗时，不保存业务响应、会话或口令。演示库数据量与采样配置相同；这些数字说明修复效果，不是生产容量承诺。

**回归测试**：

- `TelemetryQueryPlanTest`（H2）：取最新值的计划必须使用 `IX_TELEMETRY_LATEST`、按索引排序且只读 1 行，同一采样时间以较晚接收的修正值为准；累计量检查只读取本农场该指标的行（邻场和其他通道的数据量是它的十倍以上），并能检出插入的回退值。去掉索引提示后两项测试均失败。
- `DeviceAlertIntegrationTest`：按农场和整个租户读取告警都不创建事件、不写审计、不刷新已有事件时间；后台巡检后才出现离线告警，其他租户看不到。原有用例改为“后台巡检 → 读取”的生产顺序。
- `ResearchScenarioContract`（H2，配置 MySQL 时也运行）：向演示场泵站写入一次电量回退，报告计为 1 且 `consistent=false`，其他农场仍为 0；删除后恢复一致。
- `src/api.test.js`：超时（含响应体停滞）为 `slow` 而非 `offline`，随后成功即恢复 `online`；连接被拒和 504 仍为 `offline`。

## 运行指标与故障检查

使用 Spring Boot Actuator / Micrometer，HTTP 仅开放 `/api/ops/health` 与 `/api/ops/metrics`，要求现有平台管理员 Bearer 会话；租户账号返回 403，匿名请求返回 401。环境变量、配置文件、堆转储、日志文件和远程关闭端点均不开放。

| 接口或指标 | 用途 |
|---|---|
| `GET /api/health` | 兼容现有启动探针，只表示应用是否完成初始化、正在接收请求。 |
| `GET /api/ops/health/readiness` | 同时检查应用就绪状态和数据库，不返回连接详情。 |
| `GET /api/ops/metrics/http.server.requests` | 请求次数、总耗时、峰值；可按路由模板、状态码等标签筛选。 |
| `GET /api/ops/metrics/http.server.requests.percentile` | 当前进程内的 P50/P95/P99 估计；需先有请求样本。 |
| `jdbc.connections.active`、`jdbc.connections.idle`、`hikaricp.connections.pending` | 数据库连接使用量及等待；从 `/api/ops/metrics` 查看本机实际可用指标名。 |
| `jvm.memory.used`、`jvm.threads.live`、`process.cpu.usage` | JVM 内存、线程与进程负载。 |

指标以进程内存保存，重启清零，并非外部监控或告警平台。路由按模板聚合，不把农场 ID、问题正文或访问令牌作为标签。平台账号的会话和所有配置密钥仍放在原有私有文件中，不写入 Git。

排查顺序：先看请求是否在浏览器排队，再比较业务接口与瓦片耗时；检查错误率和数据库等待数；最后判断是历史查询、外网、模型网关还是设备链路。用户主动取消不等于服务离线；请求超时（顶栏“响应超时”）也不等于离线；快照时间不等于设备采样时间。H2 慢查询可对停机副本执行 `EXPLAIN ANALYZE`，比较 `scanCount` 是否随租户而非当前农场或设备增长。

## 业务日历与时区

业务日期由后端 `FarmClock` 统一提供：时区取 `farm.zone`（环境变量 `FARM_ZONE`，默认 `Asia/Shanghai`），当前时刻取可注入的 `java.time.Clock`（生产使用系统时钟，测试注入固定时钟）。服务器部署在 UTC 时，北京时间 00:00–08:00 不再把“今天”算成前一天。

- **统一口径**：今日农场的逾期判断与导航计数、运行概览与地块逐日墒情矩阵、智能农情窗口、经营简报日期与 06:00 自动补齐、灌溉每日次数上限与冷却、在种计划有效期、生产统计截止日、研究数据未来收获核查、AI 系统提示中的“今天是”，以及模拟遥测的昼夜曲线。
- **配置**：`FARM_ZONE` 须为 IANA 时区名（例如 `Asia/Urumqi`）；无效值使服务启动失败，留空沿用默认值。修改后重启。已保存的日报日期、任务到期日等日期值不会被改写。
- **仍沿用服务器时区的部分**：`start-cloud.ps1` 的 JDBC 会话偏移与 JSON 时间序列化仍跟随 JVM 时区，用于对齐数据库本地时间；`bootstrap` 目录的演示数据生成器按服务器日期生成相对日期样本，与其服务器本地时间戳配套。以 UTC 或绝对时刻保存的时间戳不受时区影响。
- **防回退检查**：`node tools/check_project.cjs scan` 拒绝后端业务代码直接调用 `LocalDate.now(...)`（`FarmClock` 与演示数据生成器除外），以及在 `FarmClock` 之外硬编码 `"Asia/Shanghai"`；规则测试位于 `tools/tests/business-time.test.cjs`。
- **UTC 回归**：`mvn test` 另起一个默认时区为 UTC 的 JVM，运行标记为 `server-utc` 的 `BusinessCalendarUtcIntegrationTest`。固定时钟位于北京时间 2026-03-15 01:00（UTC 前一日 17:00），覆盖逾期任务、每日灌溉次数、在种计划与生产统计日期边界和两条 AI 提示中的日期。单独运行：`mvn -Dtest=BusinessCalendarUtcIntegrationTest -Dsurefire.failIfNoSpecifiedTests=false test`。改回服务器时区取日期时，这 5 项回归全部失败。

- 在浏览器的瓦片读取入口挂起 4 个请求，六个业务接口仍全部返回 200；解除挂起后卫星图正常显示。此项验证前端队列隔离，不等同于真实网络带宽压测。
- 后端使用本地 HTTP 服务器模拟“已发响应头及首字节、后续响应体停顿”，验证超时后同一个工作槽可以读取下一张瓦片。
- 1366×768 下检查农场总览、智能农情及卫星图布局，未发现未捕获浏览器异常。

## 部署边界

当前本机单进程演示服务不具备跨机器高可用。正式部署需使用受维护的运行依赖、MySQL 备份与恢复演练、HTTPS 反向代理、进程管理及外部指标/告警；容量应在接近实际数据量和访问模式的独立环境验证。H2 数据文件不能同时被多个后端进程打开。升级前保存停机一致的数据备份，保留上一版本包；有 schema 变更时先在备份副本或独立测试库验证。

本轮新增索引是幂等升级；构建产物、会话、数据库备份、私有 Maven 设置和测试日志均保存在 Git 忽略目录中。
